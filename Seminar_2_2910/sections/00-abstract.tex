\begin{abstract}
\new{Large language models (LLMs) are now used to translate code between languages and to migrate it across versions, libraries and frameworks. Whether the generated code behaves like the original is decided by an oracle, and the choice of oracle can change the reported result. We present a systematic mapping study of how behavioral equivalence is evaluated in LLM-based code translation and migration, covering the main proceedings of ICSE, FSE and ASE from 2024 to 2026. From 4,451 papers we selected 49 and coded each from its full text. The most common oracles are compilation (71\%) and existing tests (57\%); formal verification, LLM-generated tests and LLM judges are rare (4\% each). Nearly a fifth of the papers use no oracle that runs the code. Oracle use differs by context: none of the 5 papers with a legacy source uses existing tests, and 9 of the 12 on library migration include a human check. Thirty-three papers report two or more oracles on the same outputs. In the 18 that give both a compile rate and a behavioral pass rate, behavior trails compilation by 3 to 98 percentage points. Ten of the 49 papers state no limitation of their own oracle. A pilot then varies only the oracle. We judged an LLM's translations of 164 HumanEval-X tasks from Python to Java with four oracles: compilation, the benchmark tests, CodeBLEU and a second LLM as judge. Depending on the oracle and its threshold, 52\% to 90\% of the same translations count as correct. The judge accepts half of those that fail the tests and even rejects 41\% of the benchmark's own reference solutions. A success rate is thus meaningful only together with the oracle that produced it. From these results we derive five gaps between evaluation practice and real migration, along with a checklist for reporting oracle provenance. We release the data and the pilot's harness.}
\end{abstract}
